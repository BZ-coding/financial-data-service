# 0005 · 数据完整性体检与举一反三（2026-11-13）

## 背景

公告重复入库（002202 实测 135 行 / 89 标题）两个多月没被发现，根因是
**所有巡检都是活性/新鲜度检查，没有一条完整性检查**。本文把同一类体检
（举一反三）推广到全部数据表与全部业务链路。

## 体检方法（可复用）

对每张数据表问三个问题：

1. **业务身份是什么？**（"同一件事"由哪几列唯一确定）
2. **数据库约束是什么？**（UNIQUE 是否覆盖业务身份）
3. **两者一致吗？**（约束 ≠ 身份 → 重复会漏网；身份无约束 → 重复会静默累积）

## 各链路的其他隐患（按类别枚举）

### A. 重复（同实体多行）
- 🔴 `mmx_search_data`：见上
- 🟡 `nav_data`：跨源同日
- 通用：所有"回填/补采"入口都必须问"重跑会不会双份"——公告表的教训就是
  采集端用了来源给的**会变**的 link 做身份

### B. 静默截断（LIMIT 不标注）
- 公告 `LIMIT 50` 已修（limit 可显式传）
- 已排查 api.py 其余 LIMIT：都是 `LIMIT 1`（取最新一条）或显式传参，无同类
- **通用规则**：返回条数 < 库内同口径条数时，响应必须带截断标注（`truncated: true` / `total`）

### C. 时区口径混用
- `CURRENT_TIMESTAMP`（UTC）vs 应用层 `datetime.now(TZ)`（+08）混用在多张表
- 已有正确处理的：catalog latest（fundflow/news 转 +08）、cleanup cutoff（按列口径取 now）
- **待统一**：凡是"窗口过滤"必须确认列是 UTC 还是本地——这是 catalog 那次修复的教训，
  每个新表都要写明口径

### D. 口径漂移（count 的含义随时间变）
- fundflow count 从"历史累计"改"本批条数"时，测试断言旧口径 → 已修（按同口径实查）
- **通用规则**：API 返回 count 必须带 `unit`/口径说明，变更口径要加 L2 字段而不是改 L1

### E. 无约束表
- `stock_fundamentals`（symbol+date 无 UNIQUE）——当前靠采集端幂等，一旦上游重发或
  重跑回填就会双份。**建议补 `(symbol, date)` 唯一索引（先体检确认 0 重复再建）**
- `subscriptions` / `collection_log` / `tickets` / `source_metrics`：操作/日志表，语义上
  允许多行，不适用

## 体检方法自身的坑（重要）

判定唯一性必须以 `PRAGMA index_list` / **主键**为准，不能靠 DDL 里有没有
`UNIQUE` 字样——`stock_fundamentals` 用的是复合主键 PRIMARY KEY(symbol, date)，
同样保证唯一，但我先前只看关键字误判为「无约束」。漏判会让「体检通过」变成假结论。

同理，唯一索引**不能**写进 schema.sql：老库有重复时 init_tables 会先于去重执行 →
IntegrityError 整段失败。这个顺序坑本轮踩了三次（announcement_id / mmx link /
nav symbol+date），统一口径：**业务唯一索引一律由 migration 建**（先去重再建索引）。
