# ADR-0003: 金融预测服务独立仓库 + 服务端 Web UI + 基本面层

**日期**: 2026-11-09
**状态**: 🧭 Draft（承接 [ADR-0002](0002-金融预测服务架构.md)，待授权落地）
**作者**: 张胜东 + Hermes
**关联**: [0002-金融预测服务架构.md](0002-金融预测服务架构.md) / [随身看板 App](https://github.com/zhangsheng377/agent-sandbox)

---

## Context

ADR-0002 把预测能力拆成独立服务，但没有回答三件事：

1. **代码该放哪** —— 继续塞在 financial-data-service 里，还是独立仓库？
2. **预测结果怎么看** —— 只有 App 端不够；每次预测、复盘、学习更新的**过程数据**需要一个专门页面来展示。
3. **除了长短期，还缺一层“基本盘”** —— 公司基本面、行业排名、宏观/政策等，这层更新频率最低，但会**同时影响长短期预测**。

---

## Decision

**三件事一起定下来**：

1. **独立仓库**：新建 `financial-prediction-service`
2. **服务端 Web UI**：提供预测历史、复盘时间线、误差归因、学习更新的可视化页面
3. **第三层预测输入：基本面层**（`fundamental`），低频更新，作为长短期预测的共同上游

---

## 1. 为什么独立仓库

| 维度 | financial-data-service | financial-prediction-service |
|------|------------------------|------------------------------|
| **职责** | 采集 + 存储 + 读接口 | 推理 + 复盘 + 学习 |
| **依赖** | 不依赖 LLM | 强依赖 FreeLLM |
| **风险** | 采集挂了影响所有下游 | 预测挂了只影响预测 |
| **发布节奏** | 稳定，极少动 | 迭代快，prompt/规则/权重频繁调 |
| **数据边界** | `market.db` | 自己的 `prediction.db` |

**结论**：独立仓库 + 独立 systemd 服务 + 独立 SQLite。**不共用 LLM key、不共用 prompt、不共用模型版本**。

## 2. 服务端 Web UI（最小集）

### 页面结构

| 页面 | 内容 |
|------|------|
| **首页 / 持仓总览** | 每个标的当前短期 / 长期 / 基本面三档预测，点击进详情 |
| **标的详情** | 预测时间线（每次预测 vs 实际走势）、复盘结论、误差归因 |
| **复盘页** | 最近 N 次预测的方向命中率 / MAE / 置信度校准 |
| **学习更新页** | `rule_patch` 列表：谁改了什么、为什么、证据链、是否已回滚 |
| **基本面页** | 公司基本盘 / 行业排名 / 关键指标 / 数据更新时间 |

### 关键交互

- **对比视图**：同一标的、同一时间窗，把「预测走势」和「实际走势」画在同一张图上
- **复盘卡片**：每次复盘一张卡，显示：预测结论、实际结果、误差类型、修正建议
- **学习更新审计**：每次 `rule_patch` 都展示 `old_value → new_value` 和触发它的 `evidence_id`
- **基本面卡**：显示「上次更新时间 / 数据来源 / 下次更新时间」，避免用户以为它是实时数据

### 页面技术栈

- 后端：FastAPI + Jinja2（与 doc-server 同风格，**不做 SPA**，保持可维护）
- 图表：服务端渲染 SVG 或 ECharts CDN（不做前端构建链）
- 认证：LAN / tailnet 免认证；公网一律 403

## 3. 三层预测输入：基本面 / 短期 / 长期

### 层次关系

```
        ┌──────────────────────────┐
        │   fundamental（基本面）    │  低频：周 / 月
        │   公司基本盘 / 行业排名     │
        └──────────┬───────────────┘
                   │
          ┌────────┴────────┐
          ▼                 ▼
  ┌──────────────┐   ┌──────────────┐
  │  short_term   │   │  long_term    │
  │  1-5 交易日    │   │  20-90 交易日  │
  └──────────────┘   └──────────────┘
```

### 基本面层要回答的问题

| 问题 | 数据来源 |
|------|----------|
| 这家公司当前处于什么行业地位？ | 行业排名 / 市占率 / 竞品对比 |
| 盈利质量如何？ | 毛利率 / 净利率 / ROE / 自由现金流 |
| 财务风险在哪？ | 负债率 / 应收账款 / 存货周转 |
| 估值贵不贵？ | PE / PB / PS / PEG |
| 政策 / 宏观对它影响多大？ | 行业政策 / 利率 / 汇率 / 上游成本 |
| 机构怎么看？ | 持仓变化 / 研报评级 / 目标价 |

### 更新频率与缓存

| 层 | 更新频率 | 触发 |
|----|----------|------|
| **fundamental** | 1 次 / 周（或财报发布时） | cron + 手动触发 |
| **short_term** | 1 次 / 交易日（盘中或盘后） | cron |
| **long_term** | 1 次 / 周 | cron |

**关键约束**：基本面层**不是实时数据**；页面必须展示「数据截止日期」，避免用户把它当实时行情看。

## 4. 数据模型增量

在 ADR-0002 基础上新增：

```sql
CREATE TABLE fundamentals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    as_of_date TEXT NOT NULL,
    industry TEXT,
    industry_rank INTEGER,
    market_cap REAL,
    pe REAL, pb REAL, ps REAL, peg REAL,
    roe REAL, gross_margin REAL, net_margin REAL,
    debt_ratio REAL,
    fcf REAL,
    institutional_holding_pct REAL,
    rating TEXT,                        -- buy / hold / sell
    summary TEXT,                       -- LLM 归因摘要
    factor_snapshot TEXT,               -- JSON：完整基本面因子
    data_sources TEXT,                  -- JSON：来源接口
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(symbol, as_of_date)
);

CREATE TABLE fundamental_snapshots (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    as_of_date TEXT NOT NULL,
    raw_payload TEXT NOT NULL,          -- 原始返回体，用于复盘
    UNIQUE(symbol, as_of_date)
);
```

预测表 `predictions` 增加字段：

```sql
ALTER TABLE predictions ADD COLUMN fundamental_id INTEGER;
ALTER TABLE predictions ADD COLUMN model_kind TEXT;  -- rule_llm / factor_llm
```

## 6. 与 App / doc-server 的关系

- **App**：继续用 `/forecast`，持仓详情页只展示「短期 + 长期」两张卡
- **doc-server**：门户反代 `/portal/proxy/financial-prediction/...`，读接口 LAN 免认证
- **Web UI**：服务自己渲染，App 不负责复杂复盘展示
- **基本面**：App 暂不展示，Web UI 单独一页；未来可在持仓详情页加一个「基本面摘要」卡

---

## 7. 举一反三：还能加什么

| 能力 | 为什么值得 |
|------|------------|
| **预测置信度校准页** | 让用户看到“高置信预测是否真的更准”，而不是被置信度骗 |
| **误差类型分布图** | 看预测主要输在“方向 / 幅度 / 数据缺失”哪一类 |
| **策略对比页** | 同一标的上跑多套策略，对比哪套更稳 |
| **异常预测提醒** | 预测置信度极高但历史准确率低的标的，主动告警 |
| **市场环境标记** | 把宏观事件（加息 / 降准 / 关税）标在时间轴上，辅助复盘 |
| **数据质量页** | 展示哪些因子经常缺失，反过来推动采集侧补数据 |

## Alternatives Considered

| 方案 | 不采用原因 |
|------|------------|
| **继续塞在 financial-data-service** | 预测迭代快、风险面大，会拖累采集线稳定性 |
| **只做 App 端展示** | 复盘/学习过程数据复杂，App 页面塞不下，也难以审计 |
| **基本面并入短期/长期模型** | 会把低频信息当成实时信号，反而降低预测质量 |
| **用 8084 存预测结果** | 采集线不该被预测结果污染 |

---

## Consequences

**正面**：预测能力有自己的**仓库、页面、数据模型、闭环**；基本面 / 短期 / 长期三层结构清晰，复盘可审计。

**代价**：多一个仓库 + 一个服务 + 一个 SQLite + 一个定时任务；需要管理 LLM 成本。

**风险**：页面复杂度上升；必须坚持「公网不暴露」「8084 只读」「预测结果不回写采集线」。
