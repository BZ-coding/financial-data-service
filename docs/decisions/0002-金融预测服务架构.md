# ADR-0002: 金融预测服务架构（长短期预测 + 自闭环复盘）

## Context

本机已有一条完整的采集 + 分析链路：

| 组件 | 作用 | 现状 |
|------|------|------|
| **8084 market-data-service** | 行情 / 资金流 / 新闻 / 告警历史 / 自定义规则 | 读接口 LAN 零认证，写接口 Basic Auth + CSRF |
| **8091 doc-server** | 报告 / 文档渲染 + 门户反代 | 已接 8084 / FreeLLM / 门户代理 |
| **dsa-mcp + alert-daemon** | 技术指标告警、行情数据消费 | stdio MCP + systemd 定时 |
| **随身看板 App** | 移动端看行情、告警、文档、单词 | 已接 8084 / 8091 / FreeLLM |
| **FreeLLM API** | OpenAI 兼容大模型推理入口 | 内网可用，支持对话/视觉 |

**缺失能力**：没有一个**独立的金融预测服务**，也没有一套**记录每一次预测、定期复盘、把预测误差反哺策略**的闭环机制。

**目标**：新增一个独立服务，让持仓里的每个标的都可以获得**短期**与**长期**两类预测；每一次预测都被记录、被复盘、被学习，逐步提升预测准确性。

---

## Decision

**新增一个独立的 `financial-prediction-service`（8090 端口），与 8084 / doc-server / FreeLLM 解耦**。长短期预测走**两套不同的输入与模型路径**，共享同一套**预测记录 + 复盘学习框架**。

### 三条核心决策

1. **长短期分离，不只分时间窗**
   - 短期（1-5 交易日）：偏技术信号 + 盘中资金流 + 突发消息，采用**规则引擎 + LLM 情绪打分**混合模型
   - 长期（20-90 交易日）：偏产业趋势 / 政策 / 宏观 / 估值 / 机构持仓，采用**因子模型 + LLM 归因**混合模型
   - 两者**不共用 prompt / 不共用权重**，由预测服务内的两个独立模块承担

2. **每次预测入库，带上下文快照**
   - 每条预测存：标的、时间、时间窗、输入因子、模型版本、输出、置信度、数据来源
   - 不只存“最终结论”，还要存“当时为何这么判断”的可复算因子快照

3. **复盘 = 数据闭环，不是人工复盘**
   - 每隔 N 天自动把预测结果与真实走势比对
   - 误差归因回写到 `prediction_feedback` 表
   - 周期性把 `prediction_feedback` 输入到下一次预测的**前置提示 / 权重 / 阈值**里
   - **不手改模型**，闭环里的规则 / 权重 / 提示都由服务自己更新

## 架构分层

```
   ┌────────────────────────────────────────┐
   │          随身看板 App (Flutter)          │
   │  持仓标的：短期预测卡 + 长期预测卡        │
   └────────────┬───────────────────────────┘
                │ HTTP GET /forecast?symbol=&horizon=
                ▼
   ┌────────────────────────────────────────┐
   │      financial-prediction-service       │
   │       (FastAPI, 端口 8090, LAN)         │
   ├────────────────────────────────────────┤
   │  /short_term   ← 规则引擎 + LLM 情绪     │
   │  /long_term    ← 因子模型 + LLM 归因     │
   │  /review       ← 定时复盘 + 误差归因     │
   │  /health       ← 服务健康               │
   └────┬──────────────┬──────────────┬──────┘
        │              │              │
        ▼              ▼              ▼
   ┌────────┐   ┌───────────┐   ┌──────────┐
   │  8084  │   │ FreeLLM    │   │ 本地 DB    │
   │ 行情/资金│   │ 大模型推理   │   │ 预测/复盘  │
   └────────┘   └───────────┘   └──────────┘
```

### 数据来源约束

| 数据源 | 用途 | 调用方式 |
|--------|------|----------|
| **8084** | 行情 / 资金流 / 新闻 / 公告 | 只走公开 GET（LAN 免认证），**绝不直连 SQLite** |
| **FreeLLM API** | 短期情绪打分 / 长期归因 | 走 OpenAI 兼容 API，密钥本地 600 权限 |
| **本地 DB** | 预测记录 / 复盘结果 / 模型版本 | 服务自己的 SQLite（`prediction.db`），不依赖 8084 的库 |

> **铁律**：预测服务**不写 8084**，也不直接读 8084 的 SQLite；所有行情输入都走 8084 的公开读接口。复盘结果也只存自己的库，不污染采集线。

---

## 短期 vs 长期：输入与模型差异

| 维度 | 短期（1-5 交易日） | 长期（20-90 交易日） |
|------|--------------------|----------------------|
| **主信号** | 技术指标、短线资金流、涨停/龙虎榜、突发消息 | 产业趋势、政策、宏观利率/汇率、估值区间、机构持仓变化 |
| **模型路径** | 规则引擎 + LLM 情绪打分 | 因子模型 + LLM 归因 |
| **数据粒度** | 分钟级 / 日级 | 周 / 月级 |
| **权重更新** | 近 20 次复盘反馈 | 近 4-8 次复盘反馈 |
| **置信度来源** | 规则命中数 + LLM 置信 + 历史准确率 | 因子一致性 + 历史准确率 |

**为什么不能共用**：短期对**噪音**敏感，长期对**因果**敏感；同一 prompt/权重会把长短期信号混淆，导致预测置信度失真。

## 预测闭环（自我复盘）

```
  ┌─────────┐    ┌──────────┐    ┌─────────────┐
  │ 预测生成  │ →  │ 预测入库   │ →  │ 定时对账      │
  └─────────┘    └──────────┘    └─────┬───────┘
                                       │
                                       ▼
                              ┌────────────────┐
                              │  误差归因 + 打分  │
                              └──────┬─────────┘
                                     │
                                     ▼
                         ┌────────────────────┐
                         │  更新规则/权重/提示词  │
                         └──────┬─────────────┘
                                │
                                ▼
                         ┌────────────────────┐
                         │  下一轮预测输入      │
                         └────────────────────┘
```

### 复盘指标

| 指标 | 含义 |
|------|------|
| **方向命中率** | 预测涨/跌 与 实际涨/跌 一致的比例 |
| **幅度误差 MAE** | 预测涨跌幅 与 实际涨跌幅 的平均绝对差 |
| **置信度校准** | 高置信预测是否真的更准（分层准确率对比） |
| **误差类型** | 判断方向对了但幅度偏小 / 方向错了 / 数据缺失 / 因子失真 |
| **时间滞后** | 信号滞后于行情的分钟/天数 |

### 反馈写入方式

- 每次复盘生成一行 `prediction_feedback` 记录
- 对连续 3 次同类误差，服务生成一条 `rule_patch`
- `rule_patch` 会在下一次同类型预测前被应用（例如：某因子权重下调 / 某个 LLM prompt 增加一条负面示例）
- 所有 `rule_patch` 都要带上 `reason` 和 `evidence_id`，保证可追溯

## 数据模型（最小集）

```sql
CREATE TABLE predictions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    horizon TEXT NOT NULL,              -- short_term / long_term
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    due_at TEXT,                        -- 预期兑现时间
    model_version TEXT NOT NULL,
    signal_score REAL,                  -- 0-100
    direction TEXT,                     -- up / down / hold
    expected_change_pct REAL,           -- 预测涨跌幅
    confidence REAL,                    -- 0-1
    reason TEXT,                        -- 模型给的判断依据（含 LLM 摘要）
    factor_snapshot TEXT,               -- JSON：当时的关键输入
    data_sources TEXT,                  -- JSON：使用了哪些接口/模型
    UNIQUE(symbol, horizon, created_at)
);

CREATE TABLE prediction_feedback (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    prediction_id INTEGER NOT NULL,
    reviewed_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    actual_direction TEXT,
    actual_change_pct REAL,
    direction_hit INTEGER,              -- 0/1
    mae_pct REAL,
    error_type TEXT,                    -- direction / magnitude / data_gap / factor_noise
    notes TEXT,
    evidence_id TEXT,                   -- 关联到具体复盘任务
    UNIQUE(prediction_id)
);

CREATE TABLE rule_patches (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    rule_kind TEXT,                     -- weight / prompt / threshold
    target TEXT,                        -- 规则名 / 提示词片段 / 因子名
    old_value TEXT,
    new_value TEXT,
    reason TEXT,
    evidence_id TEXT
);
```

## 接口契约（v0）

| Method | Path | 作用 |
|--------|------|------|
| GET | `/forecast?symbol=&horizon=short_term|long_term` | 返回当前预测 + 因子摘要 + 置信度 |
| POST | `/review?symbol=&horizon=` | 手动触发一次复盘（一般由 cron 调） |
| GET | `/health` | 依赖健康 + 最近预测成功率 |
| GET | `/rules` | 查看当前生效的规则补丁 |
| POST | `/rules/{id}/rollback` | 回滚某条规则补丁 |

> **MVP 不提供写接口给外部**，除了手动触发复盘。所有自动写都在服务内部完成。

---

## 接入 App / doc-server

- **App**：持仓详情页新增“短期预测”“长期预测”两张卡，从 `/forecast` 读
- **doc-server**：门户反代 `/portal/proxy/financial-prediction/...`，读接口 LAN 免认证
- **不进公网**：该服务默认只绑 LAN / tailnet，**不通过 Funnel / 443 对公网暴露**
- **不写 8084**：预测结果不反向写回行情库，只存自己的 DB

---

## 安全与合规边界

| 项 | 说明 |
|---|------|
| **不是投资建议** | 每次输出都要带 `disclaimer` 字段，前端固定展示 |
| **密钥隔离** | FreeLLM API key 只在预测服务配置里，600 权限 |
| **数据可追溯** | 每条预测都能还原当时的因子快照 |
| **复盘可解释** | 每条 `rule_patch` 都有 `reason` 和 `evidence_id` |
| **不删 8084 数据** | 闭环里**绝不**修改采集线数据 |

## Alternatives Considered

| 方案 | 不采用的原因 |
|------|--------------|
| **全走 LLM**（不给规则/因子） | 长短期无差异，噪声大，无法复盘归因 |
| **全走规则/因子**（不给 LLM） | 无法处理新闻/政策类非结构化信息 |
| **复用 8084 写接口** | 会让采集线承担预测职责，破坏服务边界 |
| **把预测结果写回 8084** | 采集线不应被预测结果污染 |
| **用 8084 直接接 FreeLLM** | 采集线不该管推理，风险面扩大 |

---

## Consequences

**正面**：持仓标的可获得**分层、可复盘、可追溯**的预测能力，逐步形成数据闭环。

**代价**：多一条服务线 + 一个 SQLite + 定时任务；需要控制 LLM 调用频率与成本。

**风险**：LLM 幻觉 / 数据缺失 / 误判；必须靠**复盘指标**而非“感觉”来评估效果。
