# ADR-0004: 金融预测服务设计强化 + 批评家机制

**日期**: 2026-11-10
**状态**: 🧭 Draft（承接 [ADR-0002](0002-金融预测服务架构.md) / [ADR-0003](0003-金融预测服务仓库与自学习前端.md)）
**作者**: 张胜东 + Hermes
**关联**: [0003-金融预测服务仓库与自学习前端.md](0003-金融预测服务仓库与自学习前端.md)

---

## Context

ADR-0002/0003 定了「独立仓库 / 三层输入 / Web UI / 复盘闭环」，
但还有两个关键问题没写死：

1. **“好好分析”具体意味着什么？**
   不能只是“多调几次 LLM”，必须把**预测流程拆成可审计的步骤**，
   每步都有明确输入、输出、失败模式和质量门。
2. **谁来挑战预测结果？**
   如果只有“生成者”自己评价自己，复盘就很容易变成自我合理化。
   必须引入一个**独立批评家角色**，专门挑刺、质疑、否决。

---

## Decision

**把金融预测服务设计成「多角色流水线 + 独立批评家 + 可否决输出」**。
批评家不是“另一个聊天窗口”，而是**服务内的强制质量门**。

---

## 1. 角色流水线（不是一次性调用 LLM）

```
 ┌────────────┐
 │  Planner   │  拆任务、选 horizon、决定要不要跑
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Collector  │  从 8084 拉行情 / 资金流 / 新闻 / 公告
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Feature    │  构建技术 / 资金 / 基本面 / 情绪特征
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Forecaster │  短期：规则+LLM；长期：因子+LLM
 └─────┬──────┘
       ▼
 ┌────────────┐
 │  Critic    │  独立挑刺：数据质量、逻辑漏洞、过拟合、幻觉
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Verifier   │  校验输出格式、字段完整性、置信度是否合理
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Publisher  │  入库 / 推给 App / 写审计
 └─────┬──────┘
       ▼
 ┌────────────┐
 │ Reviewer   │  事后复盘、误差归因、生成 rule_patch
 └────────────┘
```

### 每个角色的职责与失败模式

| 角色 | 输入 | 输出 | 失败模式 |
|------|------|------|----------|
| **Planner** | 触发事件 / 用户请求 / cron | 任务清单 | 重复跑 / 选错 horizon |
| **Collector** | symbol + 时间窗 | 原始数据包 | 数据缺失 / 源被封 / 时区错 |
| **Feature** | 原始数据包 | 特征表 | 指标口径错 / 缺失值处理错 |
| **Forecaster** | 特征表 | 预测 + 理由 | 幻觉 / 过拟合 / 忽略反面证据 |
| **Critic** | 预测 + 特征表 + 原始数据 | 通过 / 打回 / 降级 | 只挑表面问题 / 被 Forecaster 说服 |
| **Verifier** | 预测 + Critic 结论 | 结构化输出 | 字段缺失 / 置信度越界 |
| **Publisher** | 结构化输出 | 入库 / App 可见 | 写错表 / 泄露敏感信息 |
| **Reviewer** | 历史 + 实际结果 | rule_patch | 事后诸葛 / 过度归因 |

> **关键**：Critic 拿到的上下文**必须包含原始数据**，不能只看 Forecaster 的总结。

## 2. 批评家机制（Critic）

### 2.1 批评家的三条铁律

1. **独立上下文**
   Critic 不复用 Forecaster 的对话历史，避免被“说服”。
   它只拿：原始数据包、特征表、预测结论、Forecaster 的理由摘要。

2. **必须输出可执行意见**
   批评不是“我觉得不太好”，而是输出：
   - `blocker`：必须修，否则不许发布
   - `warning`：可以发布但要降置信度
   - `note`：记录，不影响发布
   - `missing_data`：缺哪些数据，是否值得补跑

3. **可以否决**
   如果存在 `blocker`，输出**不进入 Publisher**，任务记为 `rejected`，
   并把 reject 原因写进审计。

### 2.2 批评家的检查清单

| 类别 | 检查项 |
|------|--------|
| **数据质量** | 关键因子是否缺失？数据源是否过期？是否用了同一数据源的不同口径？ |
| **逻辑一致性** | 理由和结论是否自洽？有没有一边说“风险大”一边给高置信度？ |
| **反面证据** | 是否考虑了相反走势的可能？是否只挑了支持自己的证据？ |
| **过拟合风险** | 是否把近几天的偶然波动当成趋势？是否用了未来数据？ |
| **幻觉风险** | LLM 是否引用了不存在的事实 / 编造政策 / 编造资金流？ |
| **极端场景** | 是否考虑涨停 / 跌停 / 停牌 / 突发公告 / 宏观冲击？ |
| **置信度合理** | 高置信度是否有历史准确率支撑？是否超过历史分布？ |
| **可复现性** | 同样输入重跑，结果是否稳定？随机性是否被记录？ |

### 2.3 批评家的输出结构

```json
{
  "verdict": "pass|blocked|downgrade",
  "blockers": [
    {
      "kind": "data_gap",
      "field": "main_net_inflow",
      "reason": "关键资金流缺失，不能判断主力方向",
      "evidence": "8084 /api/v1/data 返回空",
      "fix": "等待下一轮采集或降级为 hold"
    }
  ],
  "warnings": [
    {
      "kind": "overconfidence",
      "reason": "置信度 0.92 但历史同因子准确率 0.61",
      "fix": "置信度下调到 0.7"
    }
  ],
  "notes": []
}
```

### 2.4 批评家不做什么

- **不做最终投资建议**
- **不凭空“改进”预测**：它只能挑刺、降级、否决，不能自己写一个新结论
- **不吸收 Forecaster 的自我解释**：除非 Forecaster 给出可验证证据

## 3. 服务架构增量

### 3.1 进程内多角色流水线

**不引入新的服务**，仍然是一个 FastAPI 进程内的内部编排：

```python
pipeline = [
    Planner(),
    Collector(),
    FeatureBuilder(),
    Forecaster(),
    Critic(),      # 强制
    Verifier(),    # 强制
    Publisher(),
]
```

每个角色都实现统一接口：

```python
class Role(Protocol):
    name: str
    def run(self, ctx: PredictionContext) -> RoleResult: ...
```

### 3.2 Critic 的三种实现

| 实现 | 作用 | 何时用 |
|------|------|--------|
| **规则 Critic** | 检查数据缺失、字段完整、置信度区间、重复预测 | 每次都跑 |
| **LLM Critic** | 检查逻辑一致性、反面证据、幻觉 | 每次 LLM 预测都跑 |
| **Human Critic** | 人工抽查（Web UI 上标红） | 低频 / 高风险标的 |

> **LLM Critic 必须用不同模型或不同 prompt 独立调用**，不能复用 Forecaster 的上下文。

### 3.3 数据结构增量

```sql
ALTER TABLE predictions ADD COLUMN critic_verdict TEXT;      -- pass/blocked/downgrade
ALTER TABLE predictions ADD COLUMN critic_report TEXT;       -- JSON
ALTER TABLE predictions ADD COLUMN rejected_reason TEXT;

CREATE TABLE critic_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    prediction_id INTEGER,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    critic_kind TEXT,                   -- rule / llm / human
    verdict TEXT,
    blockers TEXT,                      -- JSON
    warnings TEXT,                      -- JSON
    notes TEXT
);
```

### 3.4 复盘阶段的第二层批评

Reviewer 生成 `rule_patch` 之前，也要过一次 Critic：

- 这个 patch 是否真的解决上次误差？
- 是否会引入新的过拟合？
- 是否有足够样本支撑？
- 是否会误伤其它标的？

**Reviewer 的 patch 必须带 `evidence_id`，否则不允许入库。**

## 4. Web UI 增量

在 ADR-0003 的页面基础上，新增：

| 页面 / 区块 | 内容 |
|-------------|------|
| **Critic 报告页** | 每条预测的批评家结论：blockers / warnings / notes |
| **被打回的预测** | 展示哪些预测被 Critic 否决，为什么 |
| **置信度校准** | 高置信预测是否真的更准（分层准确率） |
| **rule_patch 审计** | 谁、何时、依据什么证据改了什么 |
| **数据质量页** | 各因子缺失率 / 时效 / 源稳定性 |
| **复盘时间线** | 预测 → Critic → 发布 → 实际结果 → patch |

---

## 5. 安全边界

| 规则 | 说明 |
|------|------|
| **Critic 不能变成第二写入口** | 它只能否决 / 降级，不能直接写预测 |
| **Critic 不能被 Forecaster 唤醒** | 避免“你帮我改一下再通过” |
| **公网不暴露** | Web UI / API 仍只 LAN / tailnet |
| **不写 8084** | 维持 ADR-0002 边界 |
| **LLM 成本可控** | Critic 只在有预测时跑，不常驻轮询 |

---

## 6. 落地步骤增量

在 ADR-0003 的 P0-P5 基础上插入：

| 阶段 | 内容 |
|------|------|
| **P2.5** | 规则 Critic（数据缺失 / 字段完整 / 置信度区间） |
| **P3.5** | LLM Critic（逻辑一致性 / 反面证据 / 幻觉检查） |
| **P4.5** | Reviewer patch 的二次 Critic |
| **P5** | Web UI 的 Critic 报告页 / 被打回预测页 / 审计页 |

---

## 7. 举一反三

| 能力 | 为什么值得 |
|------|------------|
| **Critic 自身也要被评估** | 如果 Critic 总是误报，反而拖慢流程；要统计它的 blocker 命中率 |
| **预测分版本留存** | Forecaster 原始输出 + Critic 修正后输出都要存，方便对比 |
| **对冲式预测** | 同一标的同时生成看多/看空理由，再让 Critic 裁决 |
| **数据源多样性检查** | 单一数据源是否被过度依赖 |
| **市场状态标记** | 牛市 / 熊市 / 高波动期分开统计，避免泛化错误 |
| **回放系统** | 能重放任意一次预测，看到当时每一步输入输出 |

---

## Alternatives Considered

| 方案 | 不采用原因 |
|------|------------|
| **让 Forecaster 自己评价自己** | 极易自我合理化，复盘失去意义 |
| **只靠人工审查** | 不可能覆盖每次预测；且违背“自闭环”目标 |
| **Critic 直接改预测** | 会变成第二 Forecaster，责任不清、无法审计 |
| **只做规则 Critic** | 检查不到逻辑漏洞与幻觉 |
| **只做 LLM Critic** | 检查不到结构性数据缺失 |

---

## Consequences

**正面**：预测不再是“一次性输出”，而是**可审计、可否决、可复盘**的流水线产物；
批评家提供独立第二意见，能显著降低幻觉和过度自信。

**代价**：每次预测多一步 Critic 调用；Web UI 和数据模型更复杂。

**风险**：Critic 误报会导致预测被过度否决；必须统计 Critic 自身的命中率与误报率。
